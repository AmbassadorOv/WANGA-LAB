## Purpose

WANGA Politeia is the architecture for managing, interpreting, and composing structures through their complete lineage history.

Lineage is treated not as metadata attached to an architecture, but as a source of knowledge.

Every lineage event can produce a knowledge object describing where an element came from, what it inherited, what changed, what it produced, which other lineages it integrated with, what happened after the integration, which descendants emerged, what evidence supports the transition, and what future compositions may be compatible.

The Politeia layer turns accumulated lineage history into an auditable whole-system model that can support future architectural composition.

## Foundational transformation

The architecture is structurally inspired by the principles of Plato's Politeia, but translated from a human political city into a recursive knowledge architecture.

    PLATONIC PRINCIPLE

    WANGA LINEAGE GRAPH
            ↓

            ↓

            ↓

The key transformation is:

    individual ruler expected to know the whole
                        ↓
    systemic knowledge layer reconstructing the whole
    from the histories and relations of participating lineages

## Translation-governance criterion

For the unified WANGA Computer architecture, Politeia operates before the translation layer. Its selection criterion is not an abstract ranking of models or a presumption that one model contains the best logic.

The reference is the supplied logical structure. Politeia uses lineage knowledge to select and compose computational structures according to their demonstrated ability to carry that logic into derivations with controlled error, distortion, and information loss.

```text
LINEAGE KNOWLEDGE
        ↓
WANGA POLITEIA
        ↓
TRANSLATION CONFIGURATION
        ↓
RATIONAL LOGIC
        ↓
DERIVATION
        ↓
VERIFICATION
```

This makes Politeia a governance layer for translation capability and composition, while Rational Logic remains the canonical logical reference.

## Core principles

### 1. Function before authority

A Politeia component exists because of a defined function in the architecture, not because it has unexplained authority.

Each function declares inputs, outputs, evidence requirements, lineage dependencies, validation state, and downstream effects.

### 2. Knowledge of the whole

No single lineage is assumed to contain the whole system.

The whole is reconstructed from:

    lineages
    + development events
    + inherited components
    + integration events
    + evidence
    + validation history
    + current architecture state
    + descendants

### 3. Every birth produces knowledge

The creation of a descendant is itself a knowledge-producing event.

    PARENT LINEAGE
          ↓
    TRANSFORMATION
          ↓
    NEW LINEAGE
          ↓
    NEW KNOWLEDGE
          ↓
    NEW POSSIBILITIES / CONSTRAINTS

### 4. Integration is a first-class event

When lineages combine, the combination must be explicit.

Canonical object: INTEGRATION_EVENT

Required fields:

- integration_id
- participating_lineage_ids
- reason
- inherited_elements
- introduced_elements
- conflicts
- assumptions
- resulting_lineage_ids
- architectural_destination
- source_refs
- evidence_refs
- decision_refs
- validation_state
- timestamp
- current_state

The integration event is itself a lineage node and may generate descendants.

## Functional layers

### A. Lineage Memory

Reads and exposes complete ancestry and development history.

Primary source: WANGA_LINEAGE_TREE

### B. Family Structure

Groups related architectures into branching and merging families.

Primary source: ARCHITECTURE_FAMILY_LINEAGE

### C. Knowledge Extraction

Transforms lineage events into explicit knowledge records.

Canonical knowledge forms include:

- lineage fact
- inheritance rule
- compatibility observation
- incompatibility observation
- successful integration pattern
- failed integration pattern
- transformation rule
- architectural constraint
- open question
- validated composition

### D. Whole-System Model

Builds a current graph of:

    WHO
    WHAT
    WHERE FROM
    WHAT CHANGED
    WHAT CONNECTS
    WHAT WORKED
    WHAT FAILED
    WHAT EXISTS NOW
    WHAT CAN FOLLOW

### E. Prediction

Before composing a new architecture, the system may inspect historical combinations and produce an ARCHITECTURE_PREDICTION.

Prediction records include proposed inputs, candidate parent lineages, historical analogues, compatible inherited components, known conflicts, uncertainty, reason for prediction, required validation, and resulting decision.

Prediction is advisory and must remain distinguishable from verified fact.

### F. Governance / Composition

The governance layer uses the whole-system model to structure the next composition.

It does not erase lineage history. It appends a new decision event.

Every material composition decision is therefore traceable:

    KNOWLEDGE
       ↓
    PREDICTION / ANALYSIS
       ↓
    DECISION
       ↓
    INTEGRATION
       ↓
    DESCENDANT

## The three functional orders

The Platonic three-part structure is translated into architectural functions rather than human social classes.

### 1. Integrative Order

Function: UNDERSTAND THE WHOLE

Responsibilities:

- reconstruct cross-lineage structure
- detect dependencies
- connect local knowledge to global state
- identify system-level constraints

### 2. Guardian Order

Function: PRESERVE INTEGRITY

Responsibilities:

- provenance enforcement
- lineage consistency
- evidence requirements
- validation boundaries
- conflict detection
- prevention of fabricated ancestry
- prevention of silent architecture drift

### 3. Productive Order

Function: GENERATE NEW STRUCTURES AND KNOWLEDGE

Responsibilities:

- research
- methods
- experiments
- implementations
- integrations
- descendants
- new artifacts

The three orders form one recursive system:

    PRODUCTIVE
        ↓
    new lineage knowledge
        ↓
    INTEGRATIVE
        ↓
    whole-system understanding
        ↓
    GUARDIAN
        ↓
    constraints / validation
        ↓
    PRODUCTIVE
        ↺

## Justice / functional integrity rule

The architectural translation of the justice principle is:

Each layer should perform its declared function and should not silently impersonate another layer.

Operationally:

- evidence is not a conclusion
- prediction is not a verified fact
- governance is not provenance
- lineage is not proof
- similarity is not ancestry
- architecture status is not evidence of correctness

Cross-layer transitions must be explicit.

## Compatibility knowledge

The system should learn at least four classes of composition evidence:

    COMPATIBLE
    INCOMPATIBLE
    CONDITIONALLY_COMPATIBLE
    UNKNOWN

Each compatibility observation preserves participating lineages, context, conditions, observed result, evidence, validation state, and descendant outcome.

No compatibility rule should be generalized beyond its documented scope without an explicit derivation.

## Failure modes

The Politeia should explicitly detect at least:

- FALSE_ANCESTRY — ancestry asserted without provenance
- SILENT_MERGE — integration occurred without an integration event
- KNOWLEDGE_COLLAPSE — fact, inference, and prediction are mixed
- STALE_MODEL — whole-system model no longer reflects current lineage state
- OVERGENERALIZATION — local compatibility treated as universal
- ORPHAN_DESCENDANT — descendant created without a registered parent or origin
- UNVALIDATED_PREDICTION — prediction treated as established fact
- GOVERNANCE_DRIFT — governance rules change without recorded lineage

## Validation boundary

WANGA Politeia may organize, compare, predict, and propose.

It must not silently convert a prediction into evidence.

A proposed composition becomes part of validated system knowledge only after the applicable experimental, architectural, or scientific validation process records the result.
