## Rebuild strategy

The rebuild is **architectural first, mechanical second**.

### Phase 1 — Inventory
Completed: repository estate has been inventoried and classified into architectural arcs.

### Phase 2 — Control plane
Completed:
- repository atlas
- governance rules
- automated atlas validation
- explicit non-destructive policy

### Phase 3 — Repository normalization
Next:
- inspect README and root structure
- identify original research versus upstream code
- identify duplicate/overlapping research
- connect legacy repositories to the correct research arc
- add status and provenance metadata
- standardize branch/PR conventions where appropriate

### Phase 4 — Publication graph
Then:
- connect research repositories to public research profiles
- connect publication artifacts to evidence sources
- separate public research from implementation machinery
- expose only artifacts that are sufficiently documented

### Phase 5 — Automation
Automation will continuously validate:
- repository classification
- required documentation
- evidence status
- provenance declarations
- branch/PR conventions
- research/publication links

## What will not happen automatically

- deletion of repositories
- destructive rewriting of history
- arbitrary merging of repositories
- archival based only on repository names
- presenting upstream repositories as original work
- treating a specification as verified implementation

Those actions require repository-content inspection and an architectural decision.

## Architectural principle

The GitHub estate should represent the architecture:

**Architectural intent → Research domains → Evidence → Infrastructure → Implementation → Verification → Publication**

not:

**Repository name → random code → forgotten branch**

The repository system is therefore being rebuilt as a map of the research architecture rather than as a software-project checklist.
