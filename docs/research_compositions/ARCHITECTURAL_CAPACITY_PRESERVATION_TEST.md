# Architectural Capacity Preservation Test

## Purpose

This test defines a design boundary between two system layers:

1. **Execution Engine** — automation, throughput, repeatable operations, constrained workflows.
2. **Architectural / Digital-Economic Engine** — problem definition, system composition, cross-domain synthesis, institution and infrastructure design, and creation of new system interfaces.

The objective is not to rank people. It is to prevent a system from measuring every contributor through execution throughput and thereby losing people whose primary contribution is architectural.

## Two-Track Model

### Track A — Execution / Steam-Engine Track

Characteristics:

- repeatable tasks;
- standardized interfaces;
- high-volume execution;
- workflow optimization;
- deterministic or bounded verification;
- operational scaling.

Appropriate allocation:

**Define → Delegate → Execute → Verify**

### Track B — Digital / Economic Architecture Track

Characteristics:

- new problem formulation;
- architecture creation;
- cross-domain composition;
- creation of new interfaces or institutions;
- identification of system-level failure modes;
- reconstruction of assumptions;
- design of new economic, scientific, or technical infrastructure.

Appropriate allocation:

**Observe → Define → Compose → Model → Delegate → Verify → Recompose**

A contributor should not be forced into Track A merely because Track A is easier to measure.

## Architectural Capacity Signals

A candidate should be considered for architectural work when repeated evidence shows an ability to:

- formulate problems not already represented in the workflow;
- connect concepts across otherwise separated domains;
- change the structure of a solution rather than only execute it;
- identify assumptions that the system treats as fixed;
- create useful abstractions or interfaces;
- detect contradictions between local optimization and system-level objectives;
- propose experiments that distinguish competing architectural hypotheses;
- preserve uncertainty rather than manufacture false certainty.

These are signals for investigation, not a permanent classification.

## Capacity-Loss Test

Run the same contributor through two environments:

### Environment A
A highly constrained task workflow.

### Environment B
An open architectural workspace with:

- source material;
- tools;
- evidence;
- composition primitives;
- permission to redefine the problem;
- explicit verification.

Compare the *type* of contribution, not merely the number of completed tasks.

Flag **ARCHITECTURAL_CAPACITY_LOSS** when the system causes a substantial reduction in the contributor's ability to:

- redefine the problem;
- compose a new structure;
- challenge system assumptions;
- connect domains;
- create new hypotheses;
- produce independently verifiable architectural artifacts.

The flag does not diagnose the person. It diagnoses a possible mismatch between environment and capability.

## Site / Interface Requirement

Architectural contributors need a publication and collaboration surface that is not reduced to a task queue.

Minimum interface:

**Person → Research Site → Evidence → Composition → Discussion → Prototype → Verification**

The site should support:

- long-form research;
- independent hypotheses;
- versioned artifacts;
- citations and provenance;
- cross-domain indexing;
- contact and collaboration pathways;
- links to executable experiments;
- explicit separation between hypothesis, evidence, prototype, and verification.

## Economic-System Interface

For a future digital economic layer, the system should expose architectural work as composable infrastructure rather than as a collection of micro-tasks.

Potential object types:

- Researcher;
- Architect;
- Institution;
- Evidence Artifact;
- Model;
- Test;
- Infrastructure Node;
- Financial / Risk Institution;
- Proposal;
- Verification Record;
- Collaboration Contract.

The system must not assume that every valuable contribution can be priced by task count.

## Research Hypothesis

**H1:** Systems optimized exclusively for execution throughput can under-detect contributions whose value appears primarily through architecture, recomposition, or problem formation.

This is a testable hypothesis. It requires empirical measurement rather than ideological acceptance.

## Non-Goals

This document does not:

- classify individuals permanently;
- claim that execution work is inferior;
- make claims about any named political program or individual;
- predict future economic outcomes;
- treat the two-track model as empirically proven.

The purpose is to create a falsifiable design and evaluation framework.
